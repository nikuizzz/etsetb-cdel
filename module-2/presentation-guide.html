1. The big picture

The lab builds a PIN-code lock driven by a 4x4 keypad on the DE2 board (Cyclone II EP2C35F672C6). The user presses *, then four digits, then #. The correct code is 1 2 4 8. Three wrong sequences lock the system.

3. How the keypad works

The keypad is a matrix: 4 row wires and 4 column wires. A key is a switch that connects one row wire to one column wire.

  • The columns (col[3:0]) are inputs to the FPGA, each pulled up to 3.3 V by a resistor. With no key pressed, all columns read 1.
  • The rows (row[3:0]) are driven by open-drain-style tri-state buffers: a row is driven to 0 or left at high impedance Z (the VHDL line row(i) <= '0' when rowq(i)='0' else 'Z').
  • If a row is driven to 0 and a key of that row is pressed, the column of that key is pulled to 0. If the row is Z, the key has no effect on the column.

So the row is "who we are asking" and the column is "the answer". To find a key we ask the rows one at a time and watch which column goes to 0.

Priority when several keys are pressed. Two keys of the same row: the one with the lowest column index wins (e.g. row 0: 1 > 2 > 3 > A), because the keycode assignment tests colq(0), colq(1), ... in that order. Two keys of the same column: the one with the lowest row index wins (1 > 4 > 7 > *), because rows are scanned in order 0..3 and the scan stops at the first row where a key is found.

4. part1: the keypad reader

part1 contains three things: a counter that produces a slow tick look; a 4-bit register colq that samples the columns; and the FSM whatkey that scans the rows and produces key and keycode.

The FSM states

StateMeaningrowqLeaves when
wait0Idle. No key detected; wait for the next sampling instant.1111look=1 -> check0
check0All rows driven low: is any key pressed?0000kpressed -> kra0, otherwise -> wait0
kra0..kra3Scan row 0..3 (one row driven low). If a key is found, key=1 and keycode is valid.1110, 1101, 1011, 0111kpressed -> wait1 (key found). Otherwise next row; after kra3 with no key -> wait0
wait1A key was reported. Wait one sampling period.1111look=1 -> check1
check1Is the reported key still pressed?0000still pressed -> wait1 (stay: report once); released -> wait0

Why wait1/check1 exist. If we went back to wait0 right after the report, the next sampling would find the key still pressed (the human finger takes tens or hundreds of ms) and report it again. wait1/check1 make the FSM wait for release, so one press gives one report. Why kra3 has two exits: kpressed=1 means the key is in row 3 (report it); kpressed=0 means check0 saw a key but no row confirmed it (bounce, or the key was released during the scan), so we give up and go back to wait0 without reporting.

The two registers/counters

  • look: a counter that is 1 for one clock cycle each period. The FSM only leaves wait0/wait1 when look=1, so the keypad is sampled at the counter's period, much slower than the clock. This is the handout's anti-bounce mechanism ("the keypad is checked at a much slower rate than the clock frequency").
  • colq: col sampled on the falling edge of the clock. The FSM changes row on the rising edge, so the keypad has half a clock period to settle before the FPGA reads the answer. The register therefore holds the answer to the current row. It also acts as a first synchroniser for the asynchronous col input.
  • kpressed = not (colq(3) and ... and colq(0)): "some column is 0".

The outputs

  • row: tri-state function of the state (Moore: depends only on the state).
  • key = 1 only in a kra state when colq /= 1111.
  • keycode: in krai, the position of the first 0 in colq selects one of 16 codes (row i, column j). Keypad code 0..9 digits, A..D letters, * = E, # = F.

In the original teacher's file, key/keycode are combinational (Mealy outputs: they depend on the state and on colq, so they can change on either clock edge). We changed that, see section 6.

5. The problem: contact bounce and glitches (lab 3.1)

The lab asks: "Discuss if there is any design fault that may cause fake key detections". We found two.

Fault 1: the sampling period is shorter than the contact bounce

A mechanical key does not close cleanly: for a few hundred microseconds to a few milliseconds the contact opens and closes many times ("bounce"). On the oscilloscope we measured about 400 us (15 squares of 100 us).

The teacher's part1 uses a 4-bit counter, so look is 1 once every 16 clock cycles = 16 us at the 1 MHz lab clock. That is 25 times shorter than the bounce. What happens:

  1. First contact: check0 sees the key, the scan reports it (key=1), FSM goes to wait1.
  2. 16 us later check1 samples again, but the contact is open (bounce) so kpressed=0 and the FSM goes to wait0 (it believes the key was released).
  3. 16 us later wait0 -> check0 sees the contact closed again, scans, and reports the same key again.

Result: one physical press yields several key=1 pulses, which part2 interprets as several digits. We reproduced this in simulation, by making col in the .vwf file bounce like the oscilloscope capture (part1-contact-bounce-simulation.vwf): key becomes 1 several times for one press.

Fault 2: key and keycode glitch

Because the outputs are combinational and colq updates on the falling clock edge, during the first half of a kra state colq still holds the value from the previous state. For example when a key is pressed in row 1, at the start of kra0 colq still shows the check0 result (a column at 0), so key=1 and keycode = a wrong "row 0" code for half a clock cycle, then it settles to the right value. In timing simulation we also saw a static hazard at the wait0->check0 edge. Part2 samples on the rising edge, so it does not see the half-cycle spike. But any consumer that is level-sensitive or asynchronous would take it as a fake key, and spikes on a signal that leaves the module are bad design.

6. The fix we implemented in part1

ChangeWhy
count4b -> count10b, look when the count is 1023Period = 1024 clock cycles = 1024 us at 1 MHz, about 2.5 times the measured 400 us bounce, so by the time of the next sample the contact is stable. (First we proposed 9 bits = 512 us, then chose 10 bits for a bigger safety margin.)
key/keycode registered on the rising edge (new process outreg)Removes the glitches: outputs now change only on the rising edge, once per cycle, always glitch-free. Cost: key/keycode appear one clock cycle later; part2 samples synchronously so this is harmless (we checked).

-- part1.vhd (excerpt)
counter : count10b port map ( clk => clk, nrst => nrst, output => comp);

...
outreg : process (clk, nrst)
begin
  if nrst = '0' then key <= '0'; keycode <= x"0";
  elsif clk'event and clk = '1' then key <= key_i; keycode <= keycode_i;

Verification. In the corrected simulation, one bounced press gives exactly one 1-cycle key=1 pulse with the right keycode, and no spike (check0 at 1.024 ms, kra0 at 1.025 ms, key=1 and keycode=1 at 1.026 ms).

Side effects to know. (a) A very short tap (shorter than about one look period) can be missed. (b) The first detection can take up to one look period. Both are normal for a debounced keypad. (c) count10b is a copy of the teacher's counter structure; at count 1023 the expression count+1 is out of range in strict VHDL simulators (Quartus wraps it correctly; the teacher's count4b has the same quirk at 15).

7. part2: sequence detector and error counter (lab 3.2)

Unmodified teacher's file (done by the teammate). It has two state machines and some combinational logic.

Key type detection (combinational)

  • bcdind: a decimal digit was pressed (key=1 and the code is 0..9).
  • astind: * pressed (code E). almind: # pressed (code F).

seqdet: the sequence detector

  • The code to match is the constants code1..4 = 1, 2, 4, 8; the code signal is selected by the state (start expects 1, now1x expects 2, now2x expects 4, now3x/now4x expects 8).
  • bcd_ok = a digit that matches, bcd_ko = a digit that does not match. After the first wrong digit the FSM goes along the "ko" chain, which only counts digits (the exact value no longer matters).
  • After four digits it waits for # (almind): now4ok + # -> seqok, now4ko + # -> seqko.
  • good is a flip-flop: set to 1 in seqok, cleared to 0 in start (the next *).

errcnt: the error counter

StateOn a wrong sequence (detecko)On a correct sequence (detecok)bad1 bad2 bad3
err0-> err1stay err00 0 0
err1-> err2-> err01 0 0
err2-> err3-> err01 1 0
err3stay (locked)stay (locked)1 1 1

So: three consecutive wrong sequences lock the system; a correct sequence in between resets the counter. In seqko with errcnt=err3, seqdet never leaves seqko: locked until reset.

The shift output = bcdind (a digit was entered), but forced to 0 in waiting and seqko. It is a one-cycle pulse "a digit of a sequence has been entered", intended to drive a shift register that shows the digits on the displays (we use it in 3.4).

9. 3.4: adaptation to the DE2 board (keypad_de2.vhd)

Clocking

The board has a 50 MHz clock OSC_50. With the original look counter (16 cycles) the keypad would be sampled every 320 ns, and with ours (1024 cycles) every 20 us, both far below the 10 ms bounce time the handout supposes. We therefore run the whole system on a slow clock derived with the lab's modules:

  • clock_div (teacher's): free-running 16-bit counter; each bit q[n] is a square wave of frequency 50e3 / 2n+1 kHz.
  • CLK_LOCK (teacher's, based on the altclkctrl megafunction): "functionally transparent", it tells the compiler to put the signal on a global clock line, so the divided clock reaches all flip-flops with low skew. Explained step by step in the next subsection.
  • Choice of q[10]: 50 MHz / 2048 = 24.41 kHz. With our 10-bit counter, look comes every 1024 / 24.41 kHz = 41.9 ms, well above the 10 ms of the handout's hypothesis. (We first used q[8] = 97.66 kHz, see section 15 for why it was changed after the lab test.)
  • Reset: KEY[0] (push button, active low), which matches nrst.

Clock division and CLK_LOCK, step by step

1. What clock_div really outputs. It is a binary counter that adds 1 on every rising edge of the 50 MHz clock. q[n] is simply bit n of that counter, so it is a square wave, not a "tick when the count reaches 512":

count (50 MHz cycles)012345678
q[0]010101010
q[1]001100110
q[2]000011110
  • Bit n flips every 2n cycles, so its full period is 2n+1 cycles: low for 2n cycles, then high for 2n cycles.
  • q[10]: low for 1024 cycles, high for 1024 cycles, period 2048 cycles = 40.96 us = 24.41 kHz. A circuit clocked by it sees one rising edge every 2048 cycles of the 50 MHz clock: that is the "tick". (So "divides by 2048" is right.)
  • q[15]: it does not change all the time. It flips only every 32768 cycles (0.66 ms); its period is 65536 cycles = 1.31 ms = 763 Hz. The bit that changes at every cycle is q[0] (25 MHz).

2. The problem CLK_LOCK solves. q[10] is the output of a flip-flop inside the logic of the FPGA. If we connect it straight to the clock inputs of hundreds of other flip-flops, the fitter must carry it over the normal routing wires. Those wires have a different length (so a different delay) for every destination:

  • Some flip-flops see the clock edge slightly earlier, others slightly later. This difference is called clock skew.
  • A flip-flop that fires early can change its output before a neighbour has seen the same clock edge, and the neighbour then captures the new value instead of the old one: a hold-time violation, i.e. a design that works in simulation and may fail on the chip.
  • The timing analyser also treats such a signal as ordinary data, not as a clock.

3. What CLK_LOCK is. The Cyclone II has a small number of global clock networks (16 lines): dedicated, balanced wires and buffers that reach every flip-flop in the chip with nearly the same delay, designed for exactly this. CLK_LOCK is a wrapper (generated by the Quartus MegaWizard) around the altclkctrl megafunction, i.e. the chip's clock control block, configured as "Global Clock". It has one input inclk and one output outclk.

  • Logically it does nothing: outclk is inclk. That is why the handout calls it "functionally transparent", and why it makes no difference in a functional simulation.
  • Physically it tells the compiler "this signal is a clock: put it on a global clock line", so that all the flip-flops clocked by outclk receive the edge at the same moment. The name "lock" refers to locking the signal onto that dedicated resource.
  • In our design there are two: sclk = CLK_LOCK(q[10]) for all the flip-flops of part1, part2, the digit register and the LCD request logic, and lclk = CLK_LOCK(q[15]) for LCD_int (improvement 2). The 50 MHz pin OSC_50 is already a dedicated clock pin; the blink counter uses it directly.

4. Is it really needed here? Be honest about this in the presentation: the clock is slow (24.4 kHz, a period of 41 us) and skew is on the order of nanoseconds, so this design would very probably also work without it. Quartus can also promote a high-fanout signal to a global line by itself. We use it because (a) the lab handout explicitly provides it for this purpose (lab 1: "the compiler will assign clk to a dedicated clock path"), (b) it guarantees a clean clock distribution instead of relying on a compiler heuristic, and (c) it is good practice whenever a clock is derived inside the logic.

The digits register

process (sclk, nrst)
begin
  if nrst = '0' then num <= x"FFFF"; ndig <= 0;
  elsif rising_edge(sclk) then
    if key_s = '1' and keycode_s = x"E" then       -- '*' : new sequence
      num <= x"FFFF"; ndig <= 0;                    -- all four displays blank
    elsif shift_s = '1' and ndig < 4 then          -- a digit of the sequence
      num <= num(11 downto 0) & keycode_s;          -- shift left, new digit at the right
      ndig <= ndig + 1;
    end if;
  end if;
end process;
  • It uses part2's shift exactly as the handout hints ("a display function showing the digits being entered"): shift is 1 only for digits of a sequence in progress, so digits pressed while waiting are ignored.
  • num(3:0) goes to HEX0 (rightmost). After 1, 2, 4, 8 the displays read "1 2 4 8" from left to right.
  • Why ndig < 4 (our own addition): in states now4ok/now4ko part2 keeps shift=1 for any further digit, which would push the first digit off the display. The counter ignores digits after the fourth until the next *.

The digits register and the displays, explained

0. Which displays are these? HEX0 ... HEX7 are the eight seven-segment displays of the DE2 board: the red "digital clock" style digits, not the LCD screen where text is written (that one is driven by LCD_int, improvement 2). Each display is made of 7 little LEDs called segments (a to g). Each name HEXk in the code is the 7 signals that switch the segments of display k on or off.

1. The register is a 4-digit memory. num has 16 bits = four groups of 4 bits (one group = one hexadecimal digit). Each group holds the code of one digit to show, and each group belongs to one display:

bits of num15..1211..87..43..0
goes to displayHEX3 (leftmost)HEX2HEX1HEX0 (rightmost)

2. What num <= num(11 downto 0) & keycode_s does. The symbol & is VHDL concatenation ("glue these bits together"). num(11 downto 0) is the register without its top 4 bits (the leftmost digit); gluing the new keycode_s (4 bits) on the right gives 16 bits again. In other words: every old digit moves one position to the left, the leftmost one falls out, and the new digit enters on the right. This is a shift register built with 4-bit words.

Example, the correct sequence * 1 2 4 8 # (the register value is shown in hexadecimal; F means "blank"):

The three branches of the process correspond to three situations:

  • nrst = '0': reset, everything blank.
  • key_s = '1' and keycode_s = x"E": the * key was reported by part1, so a new sequence starts: blank all displays and reset the digit counter ndig.
  • shift_s = '1' and ndig < 4: part2 says "a digit of a sequence was entered" and there is still room: shift it in and count it.

Nothing happens in the other cases, so the displays keep showing the last value (for example 1248 stays after the #, until the next *).

3. Why F means "blank". BCD7seg converts a 4-bit code into the 7 segment signals of a display. Codes 0..9 give the digit; any other code (A..F) gives 1111111. On the DE2 the segments are active low (0 = segment lit, 1 = segment off), so 1111111 turns every segment off: a blank display. We use the unused code F as "empty". 10. 3.5: the three improvements

All three follow the teacher's "previous work" report (the preliminary design we wrote before the lab).

Improvement 1 - red LEDs blinking at 1 Hz when locked (keypad_de2_i1)

  • A counter on the 50 MHz clock counts 0..24 999 999 (0.5 s) and toggles blink (a T flip-flop), giving a 1 Hz square wave.
  • A multiplexer on the red LEDs: LED_RED(i) <= blink when bad3 = '1' else (normal bad1/bad2/bad3). When bad3=1 every red LED follows blink.

Improvement 2 - LCD messages (keypad_de2_i2, part2b.vhd)

What is added to part2 (the handout says "a modified version of part2"): a flag wrong (set in seqko, cleared in start) and a message selector msg (0..5) with this priority:

Condition (priority from top)msgLCD text
errcnt = err35System Locked
seqok, or waiting and good=13Right Code!
seqko, or waiting and wrong=14Wrong Code!
waiting (other cases)1Press * to start
start ... now4ko (entering a sequence)2Enter PIN Code

part2 itself (part2.vhd) is kept untouched so that the earlier revisions still work; part2b.vhd is a copy with these additions. Inside it good is driven from an internal good_i because VHDL-93 does not allow reading an out port.

LCD_int (teacher's) writes 16 characters; we only replaced its message table with the five texts proposed in the handout (messages 1..5 above). It starts writing on a falling edge of run when it is idle (busy=0) and sets busy=1 while writing.

Why the LCD has its own, slower clock (decision)

LCD_int sends its commands one state per clock without waiting for the LCD, and an HD44780 LCD needs about 37 us per command and 1.5 ms for "clear". At 24.4 kHz each state lasts only 41 us, which is still too fast for the clear command. In lab 1 the whole design ran on q[15] (763 Hz) and the handout says "use a clock slower than q[12]". So the LCD runs on lclk = q[15] through its own CLK_LOCK (1.3 ms per state), while the keypad stays on sclk (a 763 Hz keypad would sample only every 1.3 s, with a 1024-count look).

The run / busy handshake between the two clocks

process (sclk, nrst)
begin
  if nrst = '0' then shown <= 0; run <= '1';
  elsif rising_edge(sclk) then
    if run = '1' then
      if shown /= msg and busy = '0' then run <= '0'; shown <= msg; end if;
    elsif busy = '1' then run <= '1';
    end if;
  end if;
end process;

Improvement 3 - tricking mode (keypad_de2_i3)

  • abcdind = a key among A, B, C, D was pressed (key=1 and code x"A".. x"D").
  • A T flip-flop trick toggles on every abcdind.
  • key_eff = key and not trick feeds part2b and the digit register, so while tricking, every other key is ignored. abcdind uses the raw key, so A-D can still leave the mode.
  • Display multiplexer: disp <= x"1248" when trick = '1' else num: the correct sequence is shown instead of the typed digits.
  • A, B, C, D are not digits for part2 (they are not bcdind), so they never disturb the sequence.

12. Questions the teacher may ask

Why is colq clocked on the falling edge?
The FSM drives a new row on the rising edge; the keypad (and the pull-up resistors and capacitors on the board) needs time to answer. Sampling half a period later reads the answer to the current row, so the answer and the state are aligned. Sampling on the rising edge would read the answer to the previous row.

What do wait1 and check1 do?
After reporting a key we wait one look period, then check whether the key is still pressed. If yes we keep waiting, so a held key is reported once; only on release do we go back to wait0.

Why are there two exits from kra3?
kpressed=1: the key is in row 3, validated, go to wait1. kpressed=0: check0 saw a key but no row confirmed it (bounce or release during the scan); there is no row left, so go back to wait0 without a report.

What is the design fault?
Two: (1) the 16-cycle look period is much shorter than the contact bounce, so one press gives several detections (shown in simulation with col bouncing like the oscilloscope capture); (2) key/keycode are combinational, with glitches because colq changes on the falling edge.

How did you choose 10 bits?
At 1 MHz, 210 cycles = 1024 us; measured bounce about 400 us, so about 2.5x margin. On the board with q[10] it is 42 ms, above the 10 ms assumed in 3.4.

What if a key is pressed for less than the look period?
It can be missed. That is the usual trade-off of a slow sampled keypad; human presses last tens of ms.

What is shift for?
A one-cycle pulse saying "a digit of a sequence was entered" (not in waiting or seqko). We use it to shift the digit into the display register.

What is needed to turn on the good LEDs? the locked LEDs? Can we correct wrong sequences?
good: the sequence * 1 2 4 8 #. Locked (bad3): three wrong sequences in a row; a correct sequence before the third one resets the counter to err0. Once errcnt=err3 the system stays in seqko: not correctable without reset (KEY[0]).

Why a different clock for the LCD?
LCD_int does not wait for the LCD between commands; the LCD needs tens of microseconds per command and 1.5 ms for clear, so the LCD clock must be slow (we use 763 Hz as in lab 1). The keypad needs a faster one for a reasonable response time. The run/busy handshake crosses the two.

What does CLK_LOCK do, if it does not change the signal?
It does not change the logic value; it changes where the signal travels. It puts the divided clock on the chip's dedicated global clock network, so every flip-flop gets the clock edge at almost the same time (low skew) instead of through ordinary routing wires with different delays. In simulation it is transparent.

What is q[10]?
Bit 10 of the free-running 16-bit counter in clock_div: a square wave of period 211 = 2048 cycles of the 50 MHz clock (24.41 kHz).

Why did you not modify part2?
We needed an extra output msg; we put it in a copy (part2b) so that the reports for 3.2/3.3 still describe the original.

13. Is part1 "the right thing"? The 3.4 slow-rate remark

Your concern. Section 3.4 says: "part1 should not confuse eventual rebounds with true pressed keys. One way to avoid this is checking the keypad at a slow rate. Suppose that rebounds are no more than 10 ms long, remember that the DE2 board main clock has a frequency of 50 MHz and that modules clk_lock and clock_div are available." It sounds as if debouncing had not been done in part1, so maybe part1 in 3.1 was meant to be something else.

What the original file does

The teacher's part1 is already designed around slow sampling: look is the counter output = 15 and the FSM only moves out of wait0/wait1 on look=1. The handout text of 1.1 says it explicitly: "to avoid fake detections due to possible rebounds ... the keypad is checked at a much slower rate than the clock frequency. This is done using the look signal". So the mechanism is in part1; the period is a function of the clock fed to it: period = 16 / fclk for the original count4b.

Our reading

  • The 10 ms and the "clock_div / clk_lock" remark in 3.4 describe the board-level way to reach the right period: feed part1 a slow clock (about q[14] or q[15]) instead of 50 MHz. That is consistent with the original part1; it does not imply part1 lacked the mechanism.
  • In 3.1 the lab is run at 1 MHz and asks to find and fix a fault. With the original file at 1 MHz, the sampling period (16 us) is shorter than any realistic bounce, so the fault is real in simulation. Our change makes part1 robust at any clock: the period is 1024 clock cycles.
  • Numerically, our solution and the "teacher's way" end up the same on the board: 1024 cycles at 24.41 kHz (q[10]) = 41.9 ms (16 cycles at 1.526 kHz, q[14], would give 10.5 ms). Both are above 10 ms.

What we cannot know

We cannot tell which fault the teacher has in mind in 3.1. Possibilities: (a) the 16 us period vs bounce (our fault 1); (b) the Mealy-output glitches (our fault 2); (c) something else in the FSM. Reading the FSM line by line, we did not find another path that creates a fake key independently of bounce: the held-key case is handled by wait1/check1, the kra3 fall-through returns to wait0 without reporting, and multi-key priority is deterministic. So we are fairly confident that bounce and glitches are the faults, but it is a judgement, not a certainty.

Possible concerns and how to answer

  • "You changed the teacher's part1." That is exactly what 3.1 asks ("suggest and implement a feasible alternative").
  • "In 3.4 I said to use a slow clock." We do: q[10]. Our look counter makes the final period 42 ms. If the teacher prefers the original 4-bit counter, switching count10b back to count4b and clocking with q[14] gives the same period; but the keypad would then run 64x slower (every FSM state 655 us), which is still fine for a keypad. No code was changed for this analysis.
  • Is the look period close to 10 ms? With q[10] it is 42 ms, four times the 10 ms of the hypothesis and 100 times our measured 0.4 ms bounce.

Suggestion: ask the teacher at the start of the lab session, in one sentence: "In 3.1, which design fault did you have in mind: the sampling period shorter than the bounce, or something else?" It would settle the question and costs nothing.

15. Lab finding: the keypad column RC and the clock (q[8] changed to q[10])

In the lab, with the keypad clocked by q[8] (97.7 kHz), the key A always worked, but B, C and D sometimes toggled the trick mode, which only listens to keycode = A. We read the key code on the LEDs: it was always correct when read in isolation (A=1010, B=1011, C=1100, D=1101), so the keypad was sometimes spuriously reporting A.

Hypothesis (explanation, not yet proven by a measurement): the handout says the columns have pull-up resistors and capacitors. In the state check0 all rows are 0, so a pressed key in column 3 (A, B, C or D) pulls column 3 low. In kra0 the FSM drives row 0 only and releases the other rows (tristate). Column 3 then rises back to 1 with a time constant RC. colq is sampled half a clock period later (5 us at 97.7 kHz); if column 3 has not risen yet, colq(3)=0 in kra0 is read as the key A (row 0, column 3). A is the true reading for the A key, so A was always fine; for B, C and D the false A reading from kra0 sometimes wins over the real one.

Change: keypad clock from q[8] (97.66 kHz, half period 5 us) to q[10] (24.41 kHz, half period 20 us) in all board revisions (keypad_de2 to keypad_de2_i5), since the clock was introduced in 3.4. The look period is now 1024 / 24.41 kHz = 41.9 ms. The LCD clock (q[15]) is unchanged.

Status: to be confirmed on the board (B, C, D must no longer toggle the trick mode). If it is not enough, the next option is to add a settling state in part1 after each row change.
